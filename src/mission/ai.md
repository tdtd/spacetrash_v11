# AI and Multiple Characters Mission Plan

## Purpose

This document is the focused implementation plan for AI behavior, enemy
generation, and multi-character control in **Spacetrash v11**.

The architecture now uses **upgrade-driven actor generation** and
**finite-state automata (FSA)** for behavior. Enemies are not separate types;
they are actors assembled from the same upgrade pool as player drones.
Behavior upgrades contribute FSA states and transitions.

## Goals

- Support multiple player-controlled drones/characters.
- Use behavior upgrades as FSA states rather than hardcoded AI classes.
- Create procedural enemies from modular upgrade pools.
- Enable emergent enemy behavior through combinations of sensors, effectors,
  and behaviors.
- Keep AI simple enough to run with the prototype physics and visibility
  budgets.
- Respect the **single ray instrument per agent** constraint.

## Current State

The prototype does not yet have an AI system. It has:

- `Controllable`
- `Drone`
- `Blackbox`
- `Player`
- movement input for one focused entity
- no `AiBehavior`
- no `Enemy`
- no behavior FSA
- no pathfinding

This document defines the next steps.

## Required Components

### Behavior FSA Components

Instead of a single `AiBehavior` marker, behavior is represented as FSA
states. Each behavior upgrade contributes one or more states and transitions.

For example:

- `PatrolBehavior`: `Patrol` state
- `FollowLeaderBehavior`: `Follow` state
- `GuardBehavior`: `Guard` state
- `AggressiveBehavior`: `Aggressive` state
- `FleeBehavior`: `Flee` state
- `ScavengeBehavior`: `Scavenge` state

Additionally, an `AiBehaviorState` component stores the current active
state. Transitions are driven by sensors and priorities.

### Sensor and Effector Upgrades

These are already conceptually defined for actors. For AI, key examples are:

- `CameraUpgrade` (ray instrument)
- `LightUpgrade` (emitter, not ray instrument)
- `MicrophoneUpgrade`
- `TurretWeaponUpgrade` (ray instrument if ray-based aiming)
- `RadarSensorUpgrade` (ray instrument)
- `ThermalSensorUpgrade` (ray instrument)
- movement upgrades

All actors, including AI, are subject to the **single active ray instrument**
rule.

An agent may have several non-ray upgrades (e.g., light, microphone, movement)
but only one ray instrument active at a time.

## Actor Upgrade Model

Enemies are not separate monster types. A monster is a generated actor whose
upgrades were chosen procedurally.

Enemy generation selects from weighted tables:

- base chassis
- sensory upgrades (camera, thermal, microphone, radar)
- effector upgrades (weapons, lights, tools)
- behavior upgrades (patrol, guard, aggressive, flee)
- stat modifiers

The same component system applies to player drones. This symmetry is
intentional and simplifies balance.

## AI System Boundaries

AI should be separated from physics and input.

### Input

- Player input only affects the focused controlled entity.
- AI input is generated by behavior FSA outputs.

### Movement

- Both player and AI actors use the same `Velocity`, `AngularVelocity`, and
  collision components.
- AI writes desired movement via the same `Velocity`-based interface.

### Sensors

- AI sensors feed into the shared sensor grid.
- AI does not have perfect map knowledge unless a sensor upgrade grants it.
- Each AI actor is limited to one ray instrument at a time.
- Non-ray sensors (microphones, motion detectors) may supplement.

## Behavior FSA Design

Each behavior upgrade defines a set of states and transitions. The runtime
maintains an `AiBehaviorState` component for each AI actor.

The behavior arbitration system evaluates transitions based on:

- current state
- sensor grid inputs
- health/stamina
- line-of-sight results
- proximity to goals/threats

Transitions are deterministic and data-driven.

Priority order for initial transitions (can be tuned later):

1. Flee
2. Aggressive
3. Scavenge
4. Guard
5. FollowLeader
6. Patrol
7. Passive

This order is data-driven later.

## Pathfinding

For the prototype, pathfinding should remain simple:

- Direct steering toward target with collision avoidance.
- Use sensor grid to check line-of-sight for target selection.
- No full navmesh generation required yet.
- Later, room-graph pathfinding can be added for docked ship traversal.

Pathfinding must respect actor size:

- `Small` can enter air vents.
- `Standard` and `Large` cannot enter vents.
- `Large` may be unable to pass through 1-tile doors when another actor blocks
  the path.

## Enemy Generation

### Generator Inputs

- `EnemyGenTable`
- `ProcGenContext`
- faction or ship type

### Generator Outputs

- actor entity with selected upgrade components
- starting weapon or sensor
- behavior FSA definitions
- at most one active ray instrument

Enemy generation should be deterministic from a seed.

## Implementation Steps

### Step 1: Add behavior FSA components

Add `AiBehaviorState`, `PatrolBehavior`, `GuardBehavior`,
`AggressiveBehavior`, `FleeBehavior`, `ScavengeBehavior`,
`FollowLeaderBehavior`.

### Step 2: Add behavior arbitration system

Create a system that evaluates transitions and sets `AiBehaviorState`.

### Step 3: Add FollowLeader behavior system

Create a system that moves an AI entity toward a leader entity when in
`Follow` state.

### Step 4: Add GuardLocation behavior system

Create a system that keeps an AI entity near a point and turns toward
perceived enemies when in `Guard` state.

### Step 5: Add Aggressive behavior system

Create a system that acquires a target from sensor data and moves to
attack range when in `Aggressive` state.

### Step 6: Add Flee behavior system

Create a simple health-threshold flee behavior that transitions to `Flee`
state.

### Step 7: Add Patrol behavior system

Create a waypoint patrol system for `Patrol` state.

### Step 8: Add procedural enemy generator

Use weighted tables to spawn an enemy actor from module components,
enforcing the single ray instrument limit and defining behavior FSAs.

### Step 9: Integrate pathfinding with collision

Use sensor grid and actor size to avoid impossible paths.

## BDD Scenarios

### Scenario: Enemy follows leader

- Given an enemy with `FollowLeaderBehavior`
- And a leader entity within sensor range
- When the leader moves
- Then the enemy enters `Follow` state
- And moves toward the leader
- And stops within a minimum follow distance

### Scenario: Enemy guards a location

- Given an enemy with `GuardBehavior`
- And no visible player entities
- When a player entity enters the guard radius
- Then the enemy transitions to `Guard` or `Aggressive` depending on threat
- And turns toward the player
- And if the enemy has a weapon, it attacks after entering weapon range

### Scenario: Enemy flees at low health

- Given an enemy with `FleeBehavior` and health threshold
- When the enemy health drops below the threshold
- Then the enemy enters `Flee` state
- And moves away from the current threat
- And the flee behavior takes priority over aggressive behavior

### Scenario: Procedural enemy has varied upgrades

- Given an enemy generator seed
- When an enemy is spawned
- Then the enemy has a combination of sensory, effector, and behavior
  components chosen from tables
- And no single hardcoded enemy type is used
- And the enemy has exactly one active ray instrument

### Scenario: AI uses sensors for target detection

- Given an AI actor with a visible-light camera ray instrument
- And a room with no light
- When a player moves into the room
- Then the AI does not see the player until either light improves or another
  sensor detects the player
- The sensor grid does not mark the player as visible

### Scenario: AI cannot have two ray instruments simultaneously

- Given an AI actor with a turret gun ray instrument
- When an attempt is made to equip a LIDAR or visible-light camera
- Then the previous ray instrument is unequipped or the new one is rejected
- And the actor still has exactly one active ray instrument

## Automated Arena Playtesting and Upgrade-Driven Evaluation

This section describes the approach from the broader architecture: we
should not build separate handcrafted test archetypes like “fast explorer
bot” or “cautious salvager bot”. Instead, we should build one base drone
assembler that applies upgrade modules, including behavior upgrades, and
then evaluate that drone in a generated arena.

### Core Principle

- The upgrade system underlies the AI system.
- Player drones and NPCs are assembled from the same upgrade modules.
- Behavior is an emergent property of installed upgrades and FSA states,
  not a predefined species or archetype.
- A test drone is simply a drone entity with a sampled upgrade set.

### No Hardcoded Archetypes

Do not create code like:

- `FastExplorerBot`
- `CautiousSalvagerBot`
- `CombatHeavyBot`

Instead, create:

- `ActorBuilder`
- `UpgradeRegistry`
- `BehaviorArbitration`
- `ArenaEpisode`

A “fast explorer” is simply:

- light chassis
- hover or legs movement upgrade
- maybe LIDAR
- behavior upgrade `ScavengeBehavior` or `PatrolBehavior`

A “cautious salvager” is:

- standard chassis
- wheel drive
- visible-light camera + light
- `ScavengeBehavior`
- `FleeBehavior`

The test runner should generate these configurations from the shared upgrade
pool.

### Player and NPC Symmetry

The same upgrades should drive controlled drones and generated NPCs.

If a generated NPC with a given upgrade set behaves similarly to a controlled
test drone with the same set, then the system is symmetrical.

This symmetry is a core goal and should be verified in the arena.

### Behavior Descriptors for Evaluation

Record per-episode descriptors:

- active behavior state frequency (FSA state histogram)
- sensor usage frequency
- number of distinct rooms entered
- movement style: direct / reactive / roaming / cautious
- combat avoidance vs engagement
- resource extraction rate
- cascade event count
- time spent blind
- ray instrument usage
- number of failed actions
- softlock count
- FSA transition frequencies

Do not use only win rate. Win rate overfits.

### Quality Signal

A good build should:

- produce purposeful, non-degenerate movement
- react to threats and resources
- show meaningful differences between behavior upgrades
- respect the single ray instrument constraint
- avoid spinning, wall-hugging loops, or endless fleeing
- be viable in multiple random arenas without dominating all others

### MAP-Elites Recommendation

Use MAP-Elites or another quality-diversity algorithm to discover distinct
high-quality behavior profiles.

Search dimensions:

- behavior upgrade combination
- movement upgrade
- active ray instrument or none
- weapon/effector
- chassis size
- sensor package
- level layout
- enemy distribution
- initial ship system state

Behavior descriptors form the grid cells.

Quality score rewards:

- diversity
- non-degeneracy
- meaningful interaction with systems
- recoverable cascades
- multiple viable tactics

Keep the best representative from each cell for human review.

### Arena Episode Structure

Each generated arena episode should contain:

- one generated ship or docked ship graph (using planar scaffold + WFC)
- one controlled drone assembled from sampled upgrades
- a small number of generated NPCs assembled from the same upgrade pool
- resources and hazards generated by level generation
- a goal, e.g. reach room, extract resource, survive for N ticks

Run headless with fixed timestep and deterministic random seeds.

### Validation Checks

Before evaluating behavior, filter out candidates with:

- collider penetration
- zero sensor cost
- impossible acceleration
- impossible reachability
- instant death
- permanent softlock
- behavior FSA unreachable states

These are not “interesting mechanics”; they are simulation failures.

### Immediate Next Step

The AI mission plan now includes:

- Add `UpgradeRegistry`
- Add `ActorBuilder`
- Add `BehaviorArbitration` (FSA-based)
- Add headless arena runner
- Add event logging
- Add MAP-Elites search harness

This is a major extension, but it aligns with the game’s intended design.
